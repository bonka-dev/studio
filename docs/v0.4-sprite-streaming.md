# v0.4 Sprite Streaming

This document is the source record for Bonka's v0.4 sprite-streaming work. It
is intended to support public documentation, feature pages and release notes.
It describes the implemented 8bpp GBA sprite path and its present boundaries;
it does not describe a game runtime or impose gameplay roles on projects.

## Summary

Bonka v0.4 adds a generic, streamed 8bpp OBJ-sprite path for Butano projects.
It lets a scene display and animate more independently authored sprite clips
than could be held as complete clips in the GBA's limited OBJ tile VRAM.

The runtime caches individual animation frames instead of caching a complete
clip for every visible actor. Visible actors keep their current frame resident
while the next frame is prepared. Unused frames are evicted with an LRU policy
when OBJ tile VRAM is needed.

Projects can use independently directed sprite variants and render visible
actors in screen-foot depth order without keeping full animation clips in OBJ
tile VRAM.

## User-Facing Capabilities

- Import and author directional sprite animations in the Bonka editor.
- Assign an entity definition to a sprite asset and directional set.
- Place multiple instances with a stable instance ID and authored facing angle.
- Generate GBA clip descriptors and scene sprite descriptors from Project
  Format v1 resources.
- Render many actors from shared streamed frames rather than allocating a full
  copy of an animation for each instance.
- Configure a generic directional-movement behavior through the editor's Input
  Map and Directional Movement setup. Held D-pad actions can move an actor,
  select an authored facing direction, and switch its idle/walk directional
  sets in a game-side integration.
- Keep interactive clip changes responsive while normal and background requests
  continue loading. During a clip change, the actor keeps its last valid frame
  visible until the requested clip is ready; stale prefetches cannot replace it.
- Draw overlapping scene entities in screen-foot depth order instead of JSON
  placement order.

Player and Enemy are editor/example conveniences only. Project Format, the
runtime and the GBA target do not assign gameplay behavior to those names.

## Runtime Design

The Apache-2.0 game-side API is implemented in
`packages/runtime/include/bonka/gba/streamed_sprite_runtime.h`.

### Frame Cache

`streamed_sprite_bank_manager` caches one remapped animation frame per cache
entry:

- An entry is identified by its source clip and frame index.
- Multiple actors displaying the same clip frame share that one OBJ tile
  allocation.
- An actor pins only its currently displayed frame.
- Unused frames are LRU-evictable.
- If a requested frame is unavailable, an actor keeps its last valid frame
  visible rather than displaying invalid data.
- Two cache entries remain available while ambient prefetches are queued so an
  interactive actor can replace its current frame and prefetch its successor.

Actors have independent frame indices and tick counters. Actors that start the
same clip in the same update normally appear synchronized, but frame sharing
does not require or guarantee a shared animation clock. An actor that starts
later, changes clips, or waits on streaming can be out of phase while still
sharing any frame it happens to display.

### Palette Handling

The v0.4 streamed path is an opt-in 8bpp mode. It maintains one shared OBJ
palette and deduplicates GBA RGB555 colors into stable palette slots while
cached frames reference them.

- OBJ palette index 0 remains transparent.
- Palette slots 1 through 255 are reference counted.
- A frame is remapped into the shared palette before its tiles are uploaded.
- The current 8bpp path intentionally owns the complete OBJ palette for its
  dynamic allocator.

This is a runtime policy, not a claim that the GBA cannot mix 4bpp and 8bpp
OBJ tiles. Future palette-mode work is recorded in
[`runtime-roadmap.md`](runtime-roadmap.md).

### Scheduling and Prefetch

Frame requests use three generic priorities:

| Priority | Purpose |
| --- | --- |
| `interactive` | Immediate application-driven changes, such as actor direction. |
| `normal` | Initial visible scene frames and ordinary requests. |
| `prefetch` | The next frame of an already displayed animation. |

The scheduler processes higher priorities first and uses first-in, first-out
ordering within a priority. Actors request their next animation frame while the
current frame is still visible. If the prefetched frame is ready when the frame
duration expires, the actor advances without a streaming stall. Otherwise it
holds the current frame until the requested frame arrives.

### VBlank Upload Pipeline

OBJ-VRAM writes are prepared during the normal update and committed from the
Butano VBlank callback through `bn::memory::vram_safe_copy()`.

- The default pipeline has two pending transfers.
- Its default VBlank byte budget is 2048 bytes.
- A larger single frame is allowed to occupy a transfer window on its own.
- Frame-sized staging buffers are allocated in EWRAM so they do not consume the
  constrained IWRAM stack.
- The manager exposes pending-transfer count and byte total for diagnostics.

The budget is deliberately bounded. It must be validated against real project
assets and target hardware; it is not an unlimited bandwidth guarantee.

## Scene Generation and Depth

`packages/target-gba` generates a scene descriptor for every entity with a
sprite component. Each descriptor contains:

- the stable entity `instance_id`,
- the initial generated sprite clip,
- generated screen position and facing angle, and
- the sprite-foot Y offset.

Descriptors begin in a deterministic screen-foot order. The starter keeps every
actor in one shared Butano z layer, sorts current fixed-point foot Y each frame,
and calls the actor's safe `put_above()` operation from back to front. This
allows moving actors to cross without allocating unique z-order layers.

Instance order is the stable tie-breaker for actors on the same foot line.

## Resource Model

The GBA limits remain fundamental:

- 32 KB shared OBJ tile VRAM.
- 256 shared OBJ palette entries.
- At most 128 OAM sprites total.
- At most 32 OAM sprites on one scanline.
- One hardware OAM sprite is at most 64x64 pixels.

A 32x32 8bpp frame occupies approximately 1024 bytes of OBJ tile VRAM. The
frame cache improves residency by sharing and evicting frame data, but does not
remove upload bandwidth, palette, OAM or scanline constraints. More instances
are inexpensive when they display the same cached clip frame; independently
timed clips, directions and larger frames add streaming demand.

Sprites larger than 64x64 require a future multi-OAM actor that composes
several hardware sprites. This is planned work, not part of v0.4.

## Verification

Automated checks run for this work:

- `npm test` validates Core and GBA target generation, including generated
  scene instance IDs and depth descriptors.
- `npm run build --workspace @bonka/editor` builds the editor production bundle.
- `docker compose exec -T gba make` generates and compiles the Butano ROM.
- `git diff --check` checks documentation and source whitespace.

Manual emulator acceptance has confirmed streamed multi-entity rendering,
animation, directional movement and generated Y/depth ordering. Input
responsiveness and final VBlank margins should also be checked on target
hardware before a release.

## Deliberately Out of Scope

- 4bpp-only and mixed 4bpp/8bpp OBJ graphics modes.
- Configurable palette-bank and tile-VRAM budgets for mixed modes.
- Multi-OAM actors for sprites larger than 64x64.
- Collision, AI, combat, Player or Enemy semantics.

The next planned rendering work is described in
[`runtime-roadmap.md`](runtime-roadmap.md). Entity input-to-behavior mapping is
a generic application boundary documented in
[`v0.4-input-behaviors.md`](v0.4-input-behaviors.md); it does not introduce
privileged entity roles into Project Format.
