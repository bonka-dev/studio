# v0.4 Input Behaviors

Project Format v1 entity definitions may include a generic `behavior` component.
Its required `id`, optional unique `inputActions` list, and optional scalar
`parameters` object are opaque data. Bonka validates their shape and preserves
them; Core and target generators do not assign meanings to behavior IDs or
parameter names.

Projects may list versioned input-map resources and select one with
`project.inputMap`. Input maps associate generic action IDs with GBA digital
controls and held/pressed/released triggers. They are platform mapping data,
not Player roles, movement semantics, or a runtime dispatch contract.

Core requires unique action IDs, limits each input map to 32 actions, and checks
that every entity subscription exists in the selected map. The GBA generator
assigns those actions stable `uint32_t` bits and emits GBA bindings containing a
control and held, pressed or released trigger. The runtime samples the keypad
once and resolves all active bindings into one action-state mask.

Every scene entity is emitted with its instance ID, nullable behavior ID,
resolved subscription mask, and typed string, number or boolean parameter
descriptors. Numbers use deterministic signed Q20.12 fixed-point data. This
includes entities without sprites. The target also emits every directional
sprite set in a registry keyed by sprite asset ID and set ID.

The editor's Directional Movement setup writes the ordinary behavior ID
`directional-movement`, action subscriptions, and opaque scalar parameters to
a reusable selected entity definition. Player and Enemy placement remain
editor conveniences writing ordinary definitions and instances.

That setup uses the conventional `move-up`, `move-down`, `move-left`, and
`move-right` action IDs. The editor adds any missing actions to the selected
input map with held GBA D-pad bindings, or creates and selects a default map
when the project has none. Subscribed action IDs cannot be renamed or removed
in the Input Map editor until entity definitions unsubscribe from them; bindings
remain freely editable.

The Apache runtime's generic directional helper consumes four booleans and a
positive fixed-point speed. It supports screen or isometric movement and
optional diagonal normalization, then returns a delta, moving flag and facing
angle without collision or entity semantics. A game-side integration can opt
into the opaque `directional-movement` ID, resolve parameters, action masks and
directional-set references once at startup, and perform no string work in its
frame loop. Project Format, Core, the target and runtime do not privilege that
ID or any Player role.
